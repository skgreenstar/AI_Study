PPO-KL Penalty

L = Policy objective - β · KL(πθ || πref)

Policy가 SFT Reference와 달라지는 정도에 비용을 부과합니다. 여기서 이전 iteration의 old policy와 고정 Reference Model은 구분해야 합니다.

PPO의 어려움: 여러 모델을 동시에 운용하고 completion을 새로 생성하는 on-policy 과정이 필요하며, 많은 hyperparameter와 학습 불안정·평가 지표 설계 문제가 있습니다.

별도 Reward Model 없이 Offline 선호 데이터로 학습

DPO 수식은 ‘두 개의 상대적 상승률’ 비교

Chosen 상승률
log πθ(yᵥ|x) - log πref(yᵥ|x)
－
Rejected 상승률
log πθ(yₗ|x) - log πref(yₗ|x)
L_DPO = -log σ( β [ log πθ(yᵥ|x)/πref(yᵥ|x) - log πθ(yₗ|x)/πref(yₗ|x) ] )

절대적으로 Chosen 확률만 높이는 것이 아니라, Reference와 비교했을 때 Chosen의 상대적 확률비가 Rejected보다 커지도록 합니다. β는 Reference에서 벗어나는 강도를 조절합니다.

🧯 자주 헷갈리는 개념

SFT와 Preference Tuning은 같은가?

아닙니다. SFT는 입력과 모범 응답을 직접 따라 배우고, Preference Tuning은 여러 응답 중 무엇이 더 나은지 비교 신호를 학습합니다.

RLHF의 Reward는 사람이 매번 실시간으로 주는가?

일반적인 파이프라인에서는 사람이 만든 비교 데이터로 Reward Model을 먼저 학습하고, RL 단계에서는 그 Reward Model이 많은 응답을 자동 채점합니다.

Reward와 Advantage는 같은가?

Reward는 응답의 평가 점수이고 Advantage는 현재 상태에서 예상한 baseline보다 실제 행동이 얼마나 더 좋았는지 나타냅니다.

KL Penalty는 문장 길이 차이를 재는가?

아닙니다. Policy와 Reference Model이 같은 문맥에서 내는 토큰 확률분포의 차이를 측정합니다.

DPO는 Reward Model을 전혀 사용하지 않는가?

별도로 학습된 명시적 Reward Model 없이 선호쌍으로 Policy를 직접 최적화합니다. 다만 수학적으로는 확률비 차이가 암묵적 reward 역할을 합니다.

Alignment가 완료되면 모델은 안전한가?

아닙니다. 학습 데이터 밖의 공격·오류·권한 문제는 남습니다. 모델 학습과 별도로 입력 검증·도구 권한·사람 승인·모니터링이 필요합니다.

✅ 연결 확인 퀴즈

Q1. Pairwise preference가 절대 점수보다 만들기 쉬울 수 있는 이유는?

완벽한 점수 기준을 정하는 것보다 같은 prompt의 두 응답 중 어느 쪽이 더 나은지를 비교하는 판단이 상대적으로 단순하기 때문입니다.

Q2. Reward Model의 Bradley-Terry 식에서 중요한 값은?

Chosen과 Rejected의 절대 점수가 아니라 두 reward의 차이 rᵥ-rₗ입니다.

Q3. PPO에서 Reference Model이 필요한 이유는?

Reward를 높이는 과정에서 Policy가 원래 SFT 모델의 언어 능력과 안정된 행동에서 과도하게 벗어나는 것을 KL로 제한하기 위해서입니다.

Q4. Best-of-N의 비용은 학습과 추론 중 어디에서 커지는가?

매 요청마다 N개 응답을 생성하고 채점하므로 주로 추론 비용과 지연이 커집니다.

Q5. DPO가 Chosen의 확률만 높이는 것이 아닌 이유는?

Reference 대비 Chosen의 확률 상승률과 Rejected의 상승률을 비교하여 둘의 상대적 선호 margin을 키우기 때문입니다.
