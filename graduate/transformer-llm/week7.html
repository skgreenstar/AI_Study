1. RAG: 모델에게 오픈북을 건네준다

사전학습 지식은 시점이 고정되고 문맥 창은 유한합니다. 모든 자료를 넣으면 비용이 늘고 중요한 정보가 묻힙니다. 그래서 질문과 관련된 조각만 골라 넣습니다.

Retrieve관련 조각 찾기
→
Augment질문에 근거 붙이기
→
Generate근거 기반 생성
→
Cite출처와 답 제시
이름 순서가 헷갈리는 이유: RAG는 Retrieval-Augmented Generation의 약자라 이름은 “검색으로 강화된 생성”입니다. 실제 실행 순서는 검색 → 프롬프트 보강 → 생성입니다.

3. 검색 품질은 어디를 봐야 할까?

Recall@k

빠짐없이?

전체 관련 문서 중 Top-k 안에 들어온 비율

Precision@k

쓸모있게?

Top-k 결과 중 실제 관련 문서 비율

RR@k

첫 정답이?

첫 관련 문서가 몇 등에 등장하는가

RR = 1 / rank

NDCG@k

순서까지?

관련도가 높은 문서가 위에 있는지 이상적 순위와 비교

목적에 맞춰 선택: 답을 절대 놓치면 안 되는 법률·의료 검색은 Recall을, 화면에 몇 개만 보여주는 검색은 Precision과 NDCG를 더 엄격히 봅니다. RAG 전체 평가는 검색 지표와 최종 답의 정확성·근거성을 분리해서 측정해야 합니다.

4. Tool Calling: LLM은 실행자가 아니라 호출 결정자

LLM이 함수를 직접 실행하는 것이 아닙니다. 사용할 도구와 인자를 구조화해 내보내면 애플리케이션 백엔드가 검증 후 실행하고 결과를 돌려줍니다.

① 사용자
“설비 123의 압력 알려줘”
→
② LLM 선택
get_data(id=123,
field="pressure")
→
③ Backend 실행
{"value": 4.2,
"unit": "bar"}
↓
④ LLM이 결과를 사용자 문장으로 변환
“설비 123의 현재 압력은 4.2 bar입니다.”

5. MCP: 모델과 도구 사이의 공용 어댑터

모델마다 도구 연결을 다시 만들지 않도록 Host–Client–Server 구조로 Tools, Resources, Prompts를 표준화합니다.

🖥️ MCP Host

MCP Client

MCP
공통 규약

🔌 MCP Server

Tools 실행 가능한 기능

Resources 읽을 데이터

Prompts 재사용 지시문

비유: USB 규격이 기기마다 다른 전용 케이블을 줄였듯, MCP는 AI 애플리케이션과 데이터·도구의 연결 방식을 통일합니다. 단, 표준화는 권한과 안전을 자동 보장하지 않으므로 별도 통제가 필요합니다.

6. Agent: 목표가 끝날 때까지 생각과 행동을 반복한다

한 번 함수를 부르는 Tool Calling과 달리, Agent는 실행 결과를 다시 관찰해 다음 계획을 바꿉니다. 대표 패턴이 ReAct(Reason + Act)입니다.

Input목표·사건
→
Observe현재 상태 종합
→
Plan다음 작업 결정
→
Act도구 호출
루프: Act의 결과는 다시 Observe로 들어갑니다. 목표가 충족되거나 예산·횟수·시간 제한에 도달하면 최종 Output을 냅니다.

산업 AI 예시: “설비 온도가 이상해. 조치해줘”

👁️ Observe

센서 92°C, 정상 범위 60–75°C, 최근 부하 증가 확인

🧭 Plan

센서 교차검증 → 매뉴얼 검색 → 안전한 부하 하향

🛠️ Act

보조 센서 조회, RAG 근거 확인, 승인 후 설정 변경

✅ Verify

온도 하강과 생산 영향 확인, 실행 로그와 근거 보존

7. 행동하는 AI에는 브레이크가 필요하다

답변 오류는 잘못된 텍스트로 끝날 수 있지만, 도구 오류는 메일 발송·데이터 유출·설정 변경 같은 실제 피해로 이어질 수 있습니다.

🪪 최소 권한

읽기·쓰기·삭제 권한을 분리하고 작업에 꼭 필요한 범위만 허용합니다.

🙋 사람 승인

결제, 외부 발송, 삭제, 생산 설정 변경은 실행 직전 확인받습니다.

🧱 인자 검증

LLM의 함수명과 인자를 Schema, allowlist, 범위 제한으로 검사합니다.

⏹️ 실행 한도

최대 반복 횟수·시간·비용을 두고 실패 시 안전하게 종료합니다.

🧾 관찰 가능성

검색 근거, 계획, 호출 인자, 결과, 승인자를 추적 가능한 로그로 남깁니다.

🧪 지속 평가

정상 과제뿐 아니라 Prompt Injection, 정보 유출, 잘못된 도구 선택도 시험합니다.

가장 실용적인 출발점: 처음부터 거대한 자율 Agent를 만들지 말고, 성능 좋은 모델 + 적은 도구 + 짧은 루프 + 강한 관찰성으로 시작해 평가 결과에 따라 확장합니다.

헷갈리는 개념 바로잡기

🧩 RAG와 Fine-tuning은 같은가요?

아닙니다. RAG는 실행 시 외부 문서를 문맥에 넣고, Fine-tuning은 모델 파라미터의 행동 패턴을 바꿉니다. 최신 사실·출처는 RAG, 문체·형식·반복 행동은 Fine-tuning이 보통 더 적합합니다.

🧩 Vector DB가 있으면 RAG가 완성되나요?

아닙니다. 수집·정제·Chunking·Metadata·Hybrid 검색·Re-ranking·프롬프트 구성·생성 평가까지 전체 파이프라인이 필요합니다.

🧩 Tool Calling 결과는 곧 실행 결과인가요?

아닙니다. LLM이 내놓은 것은 “이 함수를 이 인자로 호출하자”는 구조화된 제안입니다. 실제 실행과 권한 검사는 애플리케이션이 담당합니다.

🧩 Agent는 단순 챗봇과 무엇이 다른가요?

챗봇은 보통 한 입력에 한 응답을 냅니다. Agent는 목표를 위해 상태를 관찰하고 도구를 호출하며 결과에 따라 다음 행동을 여러 번 선택합니다.

🧩 MCP와 A2A 중 하나만 고르면 되나요?

역할이 다릅니다. MCP는 Agent가 도구·데이터에 연결되는 규약이고, A2A는 서로 다른 Agent가 작업을 위임하고 협업하는 규약입니다.

🧠 30초 복습

Q1. 후보 검색과 Re-ranking의 우선 목표는 각각 무엇인가요?

후보 검색은 Recall, Re-ranking은 Precision입니다.

Q2. 첫 관련 문서가 4위라면 Reciprocal Rank는?

1/4 = 0.25입니다.

Q3. LLM이 함수 호출 JSON을 만들면 누가 실제 함수를 실행하나요?

애플리케이션의 Backend/Tool runtime이 권한과 인자를 검증한 뒤 실행합니다.

Q4. ReAct의 핵심 반복은?

Observe → Plan → Act → 다시 Observe입니다.
