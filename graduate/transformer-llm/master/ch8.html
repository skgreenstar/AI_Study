다음 조각 · 9장

이 평가 기준을 글뿐 아니라 이미지·새 생성 방식에도 적용해 장단점을 비교한다.

  1. 1. 사람이 원하는 품질 기준을 정한다

    왜 필요한가 모호한 ‘좋은 답’ 대신 정확성·근거·작업 성공 등으로 나눈다.

  2. 2. 자동으로 셀 수 있는 부분을 잰다

    왜 필요한가 단어 겹침이나 정답 일치만으로도 빠른 반복 비교가 가능하다.

  3. 3. 복잡한 기준은 모델 심판으로 보조한다

    왜 필요한가 규칙이 못 잡는 의미를 평가하되 심판 편향을 따로 점검한다.

  4. 4. 측정 조건을 함께 해석한다

    왜 필요한가 점수 하나보다 데이터 오염·시도 횟수·비용·실제 업무 차이를 봐야 한다.

화살표는 이해를 위한 연결입니다. 모두를 반드시 순서대로 적용하는 시스템 구성도는 아닙니다.

생활 비유: 논술 채점

세 가지 채점 방식

교수, 키워드 채점기, 조교

사람 평가는 교수가 직접 읽는 것. 가장 정확하지만 답안 만 장은 못 읽고, 교수끼리도 점수가 갈립니다. 규칙 기반 지표는 모범 답안과 겹치는 단어 수를 세는 기계. 빠르지만 같은 뜻을 다른 말로 쓴 답을 감점합니다. LLM 심판은 채점 기준표를 받은 조교. 빠르고 이유도 적어 주지만 버릇(편향)이 있어, 교수가 가끔 조교의 채점을 검토해야 합니다.

한계. 조교는 교수와 다른 사람이지만, LLM 심판은 채점받는 모델과 같은 계열일 수 있습니다. 그러면 자기 글을 더 좋게 봅니다.
벤치마크

모의고사 성적표

벤치마크는 과목별 모의고사입니다. 국어 1등급이 수학 1등급을 보장하지 않듯, 모델마다 잘하는 축이 다릅니다. 그리고 모의고사 문제가 유출되면(데이터 오염) 점수는 실력을 말해 주지 않습니다.

굿하트의 법칙. "측정이 목표가 되면, 그것은 더 이상 좋은 측정이 아니다." 점수 올리기 자체가 목적이 되면 벤치마크는 의미를 잃습니다.

잠깐 가리고 떠올리기 · 이 개념의 역할은?

평가자끼리 기준이 맞나 — 평가자 일치도 = 같은 답을 본 사람들이 얼마나 같은 판단을 했나

사람 평가는 진실에 가장 가까운 "금" 기준이지만, 과제가 주관적입니다. 예: "생일 선물로 뭘 살까?"에 "곰 인형은 거의 항상 좋은 선물이에요. 마음에 드는 걸 고르세요."라는 답의 유용성을 두 평가자가 다르게 매길 수 있습니다.

단순 일치율(관측 일치)은 "둘 다 찍었어도 우연히 맞는 경우"를 포함합니다. 그래서 우연보다 얼마나 더 일치하는가를 봅니다: Cohen's kappa(2명), Fleiss' kappa(여러 명), Krippendorff's alpha.

프로필. 벤치마크 하나는 한 축에 대한 투영입니다. 모델마다 강점이 달라 "A는 코딩, B는 저렴"처럼 각자의 경험칙이 생깁니다. 강의 사흘 전(2025-11-18) 공개된 Gemini 3의 발표 표도 추론·코딩·도구 사용·지식 축으로 나눠 읽는 예로 쓰였습니다.

파레토 전선. 품질 대 비용·지연, 품질 대 안전, 품질 대 컨텍스트 길이 같은 맞교환에서 "더 나은 선택지가 없는" 점들의 집합. 전선 위의 모델 중에서 예산에 맞는 것을 고릅니다.

데이터 오염. 벤치마크 문제의 단서가 학습 데이터에 들어 있을 수 있습니다. 대책: 식별용 해시 문자열 심기 · 도구 사용 평가에서는 차단 목록 · 더 새로운 버전으로 평가.
교훈. 벤치마크에 과하게 기대지 말 것 · Chatbot Arena 같은 실사용 관점으로 보완 · 직접 몇 개 모델을 써 볼 것.

계산기: Pass@k 와 Pass^k

같은 모델, 같은 성공 확률인데 "한 번이라도 성공"과 "매번 성공"은 전혀 다른 숫자가 됩니다.

Pass@k
Pass^k

최소 수식 해부

수식 1

Cohen's kappa

κ = ( po − pe ) / ( 1 − pe )
κ카파우연을 뺀 일치도. 1 완전 일치, 0 우연 수준po피 오관측된 일치율pe피 이우연히 일치할 것으로 기대되는 비율
숫자 예제. 100개 응답. 둘 다 PASS 40, 둘 다 FAIL 30, 엇갈림 30.
po = 0.70. 평가자 1의 PASS 비율 0.6, 평가자 2는 0.5 →
pe = 0.6×0.5 + 0.4×0.5 = 0.50 → κ = 0.20 / 0.50 = 0.40
문장으로 읽기: 70%나 일치한 것 같지만, 찍어도 50%는 맞으므로 실제 합의는 중간 수준이다.
수식 2

BLEU와 단어 겹침

BLEU = BP × exp( (1/N) Σn=1..N log pn )
BP = min( 1, exp(1 − nref/npred) )
pn피 엔출력의 n-gram 중 참조에도 있는 비율 (n-gram 정밀도)BP비피 (brevity penalty)출력이 참조보다 짧으면 깎는 벌점nref, npred엔 레프, 엔 프레드참조와 출력의 길이
숫자 예제. 참조 "a teddy bear is reading"(5단어), 출력 "the teddy bear reads"(4단어). 겹침: teddy, bear = 2.
정밀도형 2/4 = 0.50, 재현율형 2/5 = 0.40.
1-gram만 보면 정밀도형 2/4, 재현율형(ROUGE-1) 2/5. 뜻은 거의 같은데 점수는 절반 이하이고, 겹치는 2-gram은 "teddy bear" 하나뿐이라 n을 키우면 더 낮아진다. 이것이 "문체 차이를 반영하지 못한다"는 한계다.
METEOR = Fmean × (1 − p). Fmean은 정밀도 P와 재현율 R의 가중 조화평균 PR/(αP+(1−α)R), p는 일치한 단어들이 흩어져 있을수록 커지는 벌점이다.
수식 3

가중 사실성 점수

score = Σi=1..n αi × scorei
αi알파 아이사실 i의 중요도 (합이 1)scorei스코어 아이사실 i가 참이면 1, 거짓이면 0score스코어0~1. 중요한 사실이 맞을수록 큼
문장으로 읽기: 맞은 사실의 중요도만 더한다. 위 카드 ⑤의 예: 0.3×0 + 0.4×1 + 0.2×1 + 0.1×0 = 0.60.
수식 4

Pass^k — 일관성

한 문장으로Pass^k = k번 반복해 모두 성공할 확률로 일관성 보기

작은 예 독립 성공률이 0.5면 2번 모두 성공은 0.25, 한 번 이상은 0.75다.

말을 더 풀어 보면

Pass@k는 한 번 이상, 이 장의 Pass^k는 모두 성공이다. 독립성 가정과 실제 벤치마크 정의를 함께 본다.

비유의 경계 p의 k제곱은 독립·동일 성공률 가정의 예시이며 관측된 지표를 대체하지 않는다.

잠깐 가리고 떠올리기 · 이 개념의 역할은?

@는 기회, ^는 일관성 — Pass^k = k번 반복해 모두 성공할 확률로 일관성 보기

Pass^k = C(c, k) / C(n, k)   ≈   pk
n엔한 과제를 시도한 횟수c시그중 성공한 횟수C(a, b)조합a개 중 b개를 고르는 경우의 수
숫자 예제. 10번 시도해 8번 성공(n=10, c=8), k=2 → C(8,2)/C(10,2) = 28/45 ≈ 0.62. 성공률 p=0.8로 어림하면 0.8² = 0.64로 비슷하다.
k = 8이면 p⁸ ≈ 0.17인데, 같은 모델의 Pass@8 = 1 − (1−p)⁸ ≈ 1.00이다.
문장으로 읽기: Pass@k는 "k번 중 한 번이라도"(6장), Pass^k는 "k번 모두". 고객 응대 에이전트처럼 매번 믿을 수 있어야 하는 곳에서는 Pass^k가 현실을 말한다. (조합식이 슬라이드의 정의이고, pk는 시도가 독립일 때의 어림이다.)

확인 퀴즈 3문항

답을 열기 전에 소리 내어 답해 봅니다.

Q1. 두 평가자의 관측 일치율이 0.80이고 우연 기대 일치율이 0.60이면 kappa는? 이 값은 0.80과 어떻게 다르게 읽어야 할까?
κ = (0.80 − 0.60) / (1 − 0.60) = 0.50. 겉보기 일치는 80%지만, 우연으로 설명되지 않는 부분만 보면 가능한 최대 합의의 절반 수준입니다.
Q2. Pairwise LLM 심판이 항상 먼저 제시된 응답을 고르는 것 같다. 어떤 편향이고, 어떻게 확인하고 줄일까?
위치 편향입니다. 같은 쌍을 A-B와 B-A 두 순서로 물어 선택이 순서를 따라 바뀌는지 확인하고, 두 결과를 평균해(또는 일치할 때만 채택해) 줄입니다.
Q3. 에이전트가 find_bear()라는 존재하지 않는 함수를 호출했다. 3단계 중 어디의 실패이고, 가능한 원인 셋은?
1단계 도구 예측 오류 중 "도구 환각"입니다. 원인 후보는 모델이 너무 약함(→ 모델 교체), API 이름이 직관적이지 않음(→ API 개편), 상위 지시가 불명확함(→ 지시문 수정)입니다.
